# Memory capabilities and subagent isolation

Status: accepted

Перенесённый MemoryBus гейтит запись по capability, но позволяет любому scoped view вызывать rollback — дефект исходника. Фиксируем: rollback становится отдельным правом (rollback:memory / rollback:user), не подразумеваемым write-ом; read-only потребители структурно получают отказ и на запись, и на rollback. Временные субагенты вообще не касаются памяти: родитель делает recall от их имени и добавляет в goal одноразовый неизменяемый briefing, а ребёнок запускается без memory tool, без bus handle и без пути к БД. Постоянные агенты (профили) всегда владеют своей памятью через собственный HERMES_HOME.

**Considered options:**
- Rollback под write capability: отклонено — read-only потребитель смог бы эскалироваться до rollback, нарушая структурную изоляцию, которую обещает bus.
- Прямой read-only доступ субагентов к БД: отклонено — структурная изоляция (нет handle, нет tool, одноразовая копия) надёжнее разрешительных чтений и не плодит конкурентных SQLite-писателей от множества детей.

**Consequences:** любой будущий потребитель, который должен откатывать собственные записи, обязан явно объявлять rollback capabilities; briefing субагента — фоновый контекст, а не канал памяти.
